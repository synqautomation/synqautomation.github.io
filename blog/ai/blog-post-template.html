The Single NAT Gateway Nobody Meant to Ship

It starts with one NAT Gateway in one AZ because that's what the tutorial showed. Two years and three availability zones later, it's still the only one — and it's quietly the most fragile thing in the account.

This is one of the most common findings in our AWS Networking Audits, and one of the least judgment-worthy. Nobody sits down and decides to build a single point of failure into their egress path. It happens because a NAT Gateway is something you configure once, it works, and there is rarely a reason to look at it again — until there is.

We see this pattern constantly: a production VPC spans three availability zones, every private subnet has workloads in it, and every one of those subnets routes 0.0.0.0/0 to the exact same NAT Gateway, sitting in a single AZ. It has worked for two years. That's exactly the problem — it has worked, right up until the day it doesn't.

Why this happens

Almost every getting-started guide, reference architecture, and Terraform module you'll find online deploys one NAT Gateway. It's the simplest way to get a VPC talking to the internet, and when an account is new and traffic is light, one gateway genuinely is enough. The problem isn't the decision — it's that the decision was never revisited as the environment grew.

By the time a company has real production traffic across multiple AZs, the NAT Gateway is buried three layers deep in a Terraform module nobody has opened since the initial setup. It works. Nobody has a reason to go looking for it. That's the pattern across almost every mid-market environment we've audited — not carelessness, just bandwidth spent elsewhere.

"We didn't even know we only had one until you showed us the route tables. It just — worked."

What it actually costs you

Two distinct problems live inside this one finding, and it's worth separating them clearly:

1. Availability — a single point of failure

If the NAT Gateway's availability zone has a disruption, or the gateway itself fails, every private subnet routing through it loses internet-bound connectivity — no outbound API calls, no package installs, no external service calls of any kind. This isn't a hypothetical: AZ-level disruptions happen, and NAT Gateway is a managed service, not an immortal one.

2. Cost — cross-AZ data transfer on every request

Any subnet that isn't in the same AZ as the NAT Gateway pays a cross-AZ data transfer charge on every byte of outbound traffic, on top of the NAT Gateway's own per-GB processing fee. For a workload with meaningful outbound volume — logging, third-party API calls, package registries — this adds up fast, and it's a charge that's completely avoidable.

How to check your own environment

You can confirm this in about five minutes with the AWS CLI. First, identify which AZs your private subnets with active workloads actually live in:

aws ec2 describe-subnets \
  --filters "Name=vpc-id,Values=vpc-XXXXXXXX" \
  --query 'Subnets[].[SubnetId,AvailabilityZone,CidrBlock]' \
  --output table

Then check how many NAT Gateways actually exist in that VPC, and where:

aws ec2 describe-nat-gateways \
  --filter "Name=vpc-id,Values=vpc-XXXXXXXX" \
  --query 'NatGateways[].[NatGatewayId,SubnetId,State]' \
  --output table

If the number of NAT Gateways is lower than the number of AZs with active private workloads, you have this finding. It's that direct.

SignalWhat it means
1 NAT GW, 3 active AZsSingle point of failure + cross-AZ charges on 2 of 3 AZs
NAT GW count = AZ countCorrectly distributed — no finding
Two VPCs sharing one NAT GWEnvironment isolation failure at egress — treat as High

The fix

This is a rare case where the remediation effort is genuinely low relative to the severity of the finding:

  1. Deploy one NAT Gateway per availability zone that has active private-subnet workloads.
  2. Update each AZ's route table to point to its local NAT Gateway rather than the shared one.
  3. Confirm no cross-AZ egress traffic remains by checking NAT Gateway CloudWatch metrics after the change.

There's no data migration, no downtime, and no application changes required. It's infrastructure-layer work that can typically be planned, tested, and shipped within a single sprint.

We flag this finding in almost every AWS Networking Audit we run, regardless of company size or maturity. If it's true of your environment, you're not behind — you're exactly where most fast-moving teams end up. The fix is small. The point of the audit is making sure you know it needs to happen before an AZ disruption tells you first.
